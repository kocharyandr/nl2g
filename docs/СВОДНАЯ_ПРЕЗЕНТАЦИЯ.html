SQL-агент: три роли и цикл критики

1 · СХЕМА

Выбирает таблицы

Schema Profile базы + RAG-сужение; на выход — нужные таблицы и колонки

2 · SQL

Пишет запрос

Один SELECT по суженной схеме; валидация: без DDL/DML, лимит строк

3 · КРИТИК

Выполняет и проверяет

Запускает SQL, смотрит ошибку и результат; до 3 попыток, возврат к роли 2

ОТВЕТ

таблица + SQL + пояснение на русском

Объединение дипломов · 11 · размеры по ollama list и логам diffusion_service

Три LoRA-роли в GGUF — это три полные копии базовой модели: Ollama не умеет делить базу между адаптерами. На сервере с vLLM multi-LoRA это одна база и три маленьких адаптера.

Как это работает на одной машине: три фазы

ФАЗА 1 · ДАННЫЕ И ГРАФИК

36 ГБ

3 LoRA-роли + coder, модели держатся в памяти (KEEP_ALIVE 30 мин). Ответ ≈ 1 мин. Это рабочий режим демо без правок картинок.

ФАЗА 2 · ПРАВКА ДИФФУЗИЕЙ

42 ГБ

LoRA-роли выгружены, остаются coder + FLUX. 3–4.5 мин на картинку; при автовалидации ×3 и ещё VL-модель → swap.

ФАЗА 3 · СУДЬЯ

6 ГБ

Диффузия остановлена, работает только Qwen2.5-VL. ≈ 1 мин на пару картинок.

Диск

GGUF-модели 42 ГБ + веса FLUX (трансформер 17 ГБ и текстовый энкодер) ≈ 80 ГБ; базы PAUQ, Spider, BIRD, KaggleDBQA — ещё несколько ГБ.

Цена одной машины

Один пользователь за раз; фазы переключаются скриптом; стек не переживает перезагрузку без ручного запуска; полный замер на 100 вопросов — рабочая ночь.

Масштабирование: что меняется при переезде на GPU

СЕЙЧАС

Одна рабочая станция

  • 1 пользователь, сервисы по фазам
  • LoRA = 3 копии базы по 9 ГБ
  • правка картинки 3–4.5 мин
  • 100 вопросов с правками ≈ 9 ч

ШАГ 1

Сервер с двумя GPU

  • GPU A: vLLM, одна база Qwen 14B + 3 LoRA-адаптера + VL-судья
  • GPU B: FLUX.2 Klein 9B (bf16 ≈ 18 ГБ трансформер)
  • все фазы одновременно, батчинг запросов
  • правка — [__ с] вместо минут; [__] пользователей параллельно

ШАГ 2

Кластер

  • оркестратор, executor, guardrails — реплики за балансировщиком, состояние в Redis
  • диффузия — очередь задач и автоскейл по её длине
  • LLM-пул отдельно от диффузионного
  • судья — асинхронно, после ответа

Почему делится именно так

Узкое место — диффузия: 97% времени цикла. LLM-часть отвечает за минуту и масштабируется батчингом; диффузию масштабируют числом GPU.

Что уже готово к переезду

Dockerfile и compose у каждого сервиса, OpenAI-совместимый протокол (Ollama → vLLM без правок кода), адреса сервисов в .env, диффузия уже работала на GPU-хосте Матвея.

Ограничения и следующие шаги

Что ограничивает выводы

  • Судья завышает P: AP — верхняя оценка; нужна ручная разметка части русских правок
  • 82 из 97 правок оценены: 15 упали из-за памяти, не из-за модели
  • В PAUQ почти нет динамики и рассеяний: 31 линия и 2 scatter из 780 сильных
  • Состояние чата: вопрос к базе во время ожидания «Подтвердить» уходит как правка
  • Все замеры — на одной машине, без GPU; цифры для сервера не измерены

Следующие шаги

  • Починить дату-число на стыке SQL → pandas (2 из 3 потерь)
  • Маршрутизация «вопрос к базе» по намерению, а не только по галочке
  • Переезд на GPU: vLLM multi-LoRA + отдельная GPU под FLUX, замер [__]
  • PAUQ на 300 парах и повтор правок на 3–5 seed — статистика вместо иллюстрации
  • Git-репозиторий и автозапуск стека: сейчас всё поднимается вручную
