# Сценарий демонстрации (показ научному руководителю)

Показ объединённой системы: NL2SQL-агент (ВКР 1) + агент построения графиков
(ВКР 2). Всё работает локально, интернет не нужен. Хронометраж ~12–15 минут
без вопросов.

## Рамка на 2 минуты (до того, как открыть терминал)

Тезисы, с которых стоит начать:

1. **Что объединено.** Конвейер из ВКР 1 (схемотехник → программист → критик,
   LoRA на роли) завёрнут в отдельный HTTP-сервис и подключён к системе из
   ВКР 2 как третий источник данных — наравне с текстом и загруженным CSV.
   Ни одна из работ не переделывалась: интеграция через контракт.
2. **Ключевой перенос из ВКР 1** — execution feedback: SQL реально исполняется
   до показа пользователю, критик чинит запрос по ошибке движка.
   Наружу не выходит неисполнимый запрос.
3. **Ключевой перенос из ВКР 2** — «LLM решает как, код делает что»: модель
   генерирует pandas/matplotlib-код, исполняет его детерминированная среда.
   Цифры на графике нельзя «нафантазировать».
4. **Воспроизводимость.** В ВКР 1 — 57.3% execution accuracy; контрольный
   прогон этой сборки на 40 гольд-вопросах — 55% (инференс через другое
   квантование). Разбор прогона — отдельная страница с ручной разметкой.
5. **Новое сверх обеих ВКР:** мультибазовый сервис (244 базы за одним
   endpoint), работа с русскоязычной схемой БД, обязательный показ SQL
   пользователю под графиком.

Полезно держать открытыми: `integration_presentation.html` (слайды),
`sql_agent/review.html` (разбор прогона).

## Подготовка (за 10 минут до показа)

```bash
# 1. Ollama с тремя LoRA-моделями
OLLAMA_MAX_LOADED_MODELS=3 OLLAMA_KEEP_ALIVE=30m ollama serve &

# 2. Сервис данных (конфигурация в sql_agent/.env, русская база — по умолчанию)
cd sql_agent && make run &          # :8500

# 3. Оркестратор
cd ../chart_agent && OPENAI_API_BASE=http://127.0.0.1:11434/v1 \
  OPENAI_API_KEY=ollama OPENAI_MODEL_NAME=qwen2.5-coder:14b \
  SQL_AGENT_ENABLED=true SQL_AGENT_URL=http://127.0.0.1:8500 \
  STATE_STORE_REDIS_ENABLED=false LANGFUSE_ENABLED=false \
  GUARDRAILS_ENABLED=false EDIT_USE_STUB=true \
  .venv/bin/python -m uvicorn app.main:app --port 8010 &

# 4. Чат
cd ../chat && CHART_AGENT_URL=http://127.0.0.1:8010 CHAT_REQUEST_TIMEOUT=900 \
  GRADIO_SERVER_PORT=7861 GRADIO_ANALYTICS_ENABLED=False .venv/bin/python app.py &
```

Проверка одной строкой (должно быть четыре «200»):

```bash
for u in localhost:11434/api/tags localhost:8500/health localhost:8010/docs localhost:7861; \
  do curl -s -o /dev/null -w "%{http_code} $u\n" --max-time 4 $u; done
```

Прогрев: задайте один вопрос через CLI, чтобы модели загрузились в память —
иначе первый ответ на показе займёт не 20 секунд, а две минуты:

```bash
cd sql_agent && ./scripts/ask.py "выручка по городам за год"
```

## Часть 1 · Русская база через CLI (~3 мин)

База «РозничнаяСеть» — 8 магазинов, 10 товаров, продажи за 2025 год.
Русские **имена таблиц и колонок**: `магазины(город, формат)`,
`товары(название, категория, цена)`, `продажи(месяц, количество, выручка)`.

```bash
./scripts/ask.py --schema          # показать русскую схему с описаниями
./scripts/ask.py "выручка по городам за год, по убыванию"
```

Ожидание: ~20 с, JOIN двух таблиц, Москва 2 771 040 ₽ впереди.
Что проговорить: SQL сгенерирован моделью с LoRA из ВКР 1, **исполнен реально**
до показа (петля критика), «попыток критика: 1» = сработало с первого раза.

## Часть 2 · Чат: график по данным из базы (~5 мин)

Открыть http://localhost:7861, поставить галочку **«Данные из базы»**.

1. `построй график выручки по городам`
   → ~1 мин, столбчатая диаграмма, под ней пояснение и раскрывающийся SQL.
   Проговорить: пользователь видит запрос, по которому построен график, —
   цифрам из базы нельзя верить вслепую (у конвейера 57% точности на бенчмарке).

2. `Подтвердить` → затем: `построй график динамики выручки по месяцам`
   → видна сезонность: провал в январе–феврале, пик в декабре.

3. `а теперь линией`
   → график перестраивается **без повторного похода в базу** — строки
   переиспользуются из состояния сессии, цифры не могут молча измениться.

## Часть 3 · Английские бенчмарки и разбор (~4 мин)

```bash
./scripts/ask.py -d TheHistoryofBaseball "How many players weigh over 200 pounds?"   # 4584
./scripts/ask.py --list | head          # 244 базы: KaggleDBQA + Spider + BIRD + демо
```

Открыть `sql_agent/review.html` — разбор прогона 40 гольд-вопросов:
авто-EX 55% (в ВКР — 57.3%), ручная разметка «точность» и «шаблон»,
таблица «что откуда» — какой этап какой моделью сделан и из чьего диплома.

## Запасные ходы

| Если | То |
| --- | --- |
| модель отвечает > 2 мин | модели выгрузились — прогрев из «Подготовки» |
| «Сервис данных недоступен» | `cd sql_agent && make run`; это честный отказ, не деградация — можно и показать |
| вопрос вернул только текст | система сама дозапросит число; если нет — добавить «по количеству» |
| чат завис | обновить страницу; сессия хранится на сервере |

## Часть 4 · Диффузионное улучшение графика (опционально, ~3 мин)

Требует весов FLUX.2 [Klein] 9B (gated: на HF-аккаунте должна быть принята
лицензия) и ~20 ГБ свободной unified memory. Сервис портирован на Apple
Silicon (MPS), но на Маке генерация занимает минуты — для живого показа
надёжнее заранее сгенерированная пара «до/после».

```bash
cd diffusion_service && HF_TOKEN=hf_... .venv/bin/python app.py &   # :8001
# у оркестратора: EDIT_USE_STUB=false DIFFUSION_MODEL_NAME=flux DIFFUSION_PORT=8001
```

В чате: подтвердить график → попросить «улучши оформление». Что проговорить:
диффузия применяется **только к уже построенному графику** (LoRA из ВКР 2
обучен держать правки минорными), прямой генерации данных диффузией в системе
нет по построению.

## Что сознательно НЕ показываем

- Живую диффузию, если веса не скачаны или память занята LLM-моделями —
  тогда только пара «до/после» (см. часть 4).
- Guardrails и Redis — выключены для простоты локального запуска.
- Hard-вопросы бенчмарка (вложенные подзапросы): точность там 0–12%, и это
  честно написано в review.html.
