## 1. Идея

Сейчас у системы два источника данных: текст пользователя («A=10 B=20 C=15») и
загруженная таблица CSV/TSV. Предлагается третий: **SQL-агент** — отдельный
сервис, подключённый к базе, который по запросу на естественном языке возвращает
готовую таблицу. `chart_agent` дальше строит по ней визуализацию своим обычным
пайплайном.

```text
"покажи выручку по регионам за прошлый квартал"
        │
        ├─ текст        → text_data_extractor   (есть)
        ├─ CSV от юзера → table_data_extractor  (есть)
        └─ SQL-агент    → table_data_extractor  (предлагается)
                              │
                              └→ plot_creator → рендер → подтверждение → диффузия
```

Ключевое: **новый сервис поставляет только данные**. Он не решает, какой строить
график, не генерирует `matplotlib`-код и не участвует в подтверждении результата.
Всё это уже умеет `chart_agent`. Чем уже зона ответственности нового сервиса, тем
дешевле интеграция.

Зачем отдельным сервисом, а не веткой внутри оркестратора: доступ к базе —
отдельный контур безопасности (креды, роли, сетевой доступ, аудит запросов), и
его не стоит смешивать с оркестратором, который ходит в LLM и рендерит картинки.
Это та же логика, по которой в отдельные сервисы вынесены исполнение кода и
GPU-инференс.

## 2. Точка подключения

Хорошая новость: **табличный путь уже существует и не зависит от того, откуда
пришла таблица.** Подключение — это по сути ещё один способ наполнить одно поле
состояния.

Развилка источника — одна строка в [chart_agent/app/graph/nodes/interaction_node.py:117](chart_agent/app/graph/nodes/interaction_node.py#L117):

```python
if decision.target_stage == StageName.data_parsing:
    return "table_data_extractor" if (state.user_csv_data or state.persisted_csv) else "text_data_extractor"
```

Дальше `table_data_extractor` (`app/graph/nodes/table_node.py`) делает:

1. `parse_table()` — детерминированно читает CSV/TSV в `DataFrame`;
2. `build_table_prompt_context()` — компактный контекст (размерность, `df.info`,
   markdown-превью первых строк);
3. LLM генерирует pandas-код (`TableCodeSpec`);
4. код исполняется в ограниченном окружении;
5. `dataframe_to_dataset_spec()` → `DatasetSpec` + `ChartIntent` + отчёт валидации;
6. дальше обычный `plot_creator`.

**Шаги 2–6 переиспользуются как есть.** Нужен только новый шаг 1: вместо парсинга
CSV — вызов SQL-сервиса и получение `DataFrame`.

Это даёт два принципиально разных варианта интеграции.

### Вариант А (рекомендуемый): SQL-сервис отдаёт «сырую» таблицу

Сервис выполняет SQL и возвращает результат как есть, без предварительной
агрегации под график. `chart_agent` дальше сам решает, как из этой таблицы
получить данные для конкретного типа графика — через уже работающий codegen-шаг.

- плюсы: минимум изменений, вся логика подготовки под график остаётся в одном
  месте, поведение идентично загруженному CSV;
- минусы: если выборка большая, она целиком едет по HTTP и лежит в состоянии сессии.

### Вариант Б: SQL-сервис отдаёт уже агрегированную таблицу

Сервис сам делает `GROUP BY` и возвращает готовые `x`/`y`/`series`.

- плюсы: агрегация уезжает в базу, по сети едет мало;
- минусы: два места принимают решение о форме данных, и их надо согласовывать;
  ломается сценарий «а теперь то же самое, но линией» без повторного похода в базу.

**Рекомендация — вариант А**, с ограничением размера выборки на стороне сервиса
(`LIMIT` + порог по числу строк). Вариант Б имеет смысл как оптимизация позже,
если упрётесь в объёмы.

## 3. Контракт нового сервиса

Предлагаемый минимум — один эндпоинт, синхронный, без состояния.

**`POST /query`**

```json
{
  "question": "выручка по регионам за прошлый квартал",
  "session_id": "uuid-сессии-из-chart_agent",
  "max_rows": 5000,
  "hints": { "schema": "public", "tables": ["orders", "regions"] }
}
```

**Ответ (успех):**

```json
{
  "status": "ok",
  "columns": [
    { "name": "region",  "type": "string" },
    { "name": "revenue", "type": "number" }
  ],
  "rows": [["North", 7650.0], ["South", 2100.0]],
  "row_count": 4,
  "truncated": false,
  "sql": "SELECT region, SUM(revenue) ... GROUP BY region",
  "explanation": "Суммарная выручка по регионам за 2025-Q4"
}
```

**Ответ, когда вопрос непонятен:**

```json
{
  "status": "need_clarification",
  "question_to_user": "За какой период? В данных есть 2024 и 2025 год."
}
```

**Ответ при ошибке:**

```json
{ "status": "error", "error_type": "sql_error", "message": "column \"revenu\" does not exist" }
```

Требования к контракту:

- **`columns` + `rows` вместо CSV-строки.** Типы колонок приходят от базы — это
  надёжнее, чем угадывать их из текста. У `chart_agent` эвристика определения
  типов уже подводила (см. п.15 README оркестратора), и здесь её лучше не задействовать.
- **`sql` и `explanation` обязательны** даже при успехе: их нужно показать
  пользователю («вот по какому запросу построено») и записать в трейс Langfuse.
- **`truncated`** — честный флаг, что выборка обрезана по `max_rows`. Строить
  график по обрезанным данным без предупреждения нельзя.
- **`need_clarification` как штатный ответ, а не ошибка.** У оркестратора уже есть
  механизм уточняющих вопросов, его надо переиспользовать (см. п.4.4).
- **Дополнительно `GET /schema`** — список таблиц и колонок. Нужен, чтобы
  `interaction` мог понять, отвечает ли вопрос вообще на данные этой базы.

## 4. Что менять в `chart_agent`

### 4.1. Конфигурация

`app/core/config.py` — по образцу существующего блока guardrails:

```python
sql_agent_enabled: bool  = Field(default=False, alias="SQL_AGENT_ENABLED")
sql_agent_url: str       = Field(default="",    alias="SQL_AGENT_URL")
sql_agent_timeout_sec: float = Field(default=60.0, alias="SQL_AGENT_TIMEOUT_SEC")
sql_agent_max_rows: int  = Field(default=5000, alias="SQL_AGENT_MAX_ROWS")
```

Флаг `sql_agent_enabled=False` по умолчанию — при выключенном сервисе система
ведёт себя ровно как сейчас.

### 4.2. Клиент

Новый `app/infra/sql_agent/client.py` — берите за образец
`app/infra/guardrails/client.py`: `httpx.AsyncClient`, таймаут из настроек,
обёртка в `node_span` для Langfuse, понятная политика при недоступности сервиса
(здесь fail-open не годится: без данных строить нечего, нужно честное сообщение
пользователю).

### 4.3. Маршрутизация

Развилку в `route_after_interaction` нужно расширить третьей веткой. Решение
«это вопрос к базе» принимает `interaction`:

- быстрый путь — zero-shot классификация через `guardrails_api`
  (`POST /api/v1/classify/custom` с метками вроде `chart_from_text` /
  `chart_from_table` / `chart_from_database` / `image_edit`), уверенность сверяется
  с `GUARDRAILS_CONFIDENCE_THRESHOLD`;
- при низкой уверенности — LLM, как сейчас.

Потребуется добавить значение в `InteractionAction`/целевые стадии
(`app/graph/node_schemas/interaction_node.py`) и новую стадию `sql_query` в
`app/domain.py` — стадия нужна, чтобы отличать «ждём ответа от базы» в UI и в
rollback.

### 4.4. Новая нода

`app/graph/nodes/sql_source_node.py`:

```text
sql_source:
  1. вызвать SQL-сервис
  2. status=need_clarification → уйти в interaction с вопросом пользователю
     (тот же путь, что у существующего clarification)
  3. status=error → stage=error + понятное сообщение
  4. status=ok → columns+rows превратить в DataFrame,
     положить в состояние и уйти в table_data_extractor
```

В графе (`app/graph/pipeline.py`):

```python
graph.add_node("sql_source", _sql_source, retry_policy=llm_retry)
graph.add_conditional_edges("sql_source", route_after_sql_source, {
    "table_data_extractor": "table_data_extractor",
    "clarification": "interaction",
    "error": "error",
})
```

### 4.5. Состояние

В `AppState` (`app/graph/state.py`) рядом с `user_csv_data` / `persisted_csv`:

- `sql_result_table` — полученная таблица (сериализуемая: `columns` + `rows`);
- `sql_query_text` и `sql_explanation` — чтобы показать пользователю и не
  потерять при повторных ходах диалога;
- `persisted_sql_result` — по аналогии с `persisted_csv`, чтобы правка «а теперь
  линией» не ходила в базу повторно.

⚠️ **Состояние сессии целиком сериализуется в Redis.** Большая выборка раздует
каждую запись состояния. Отсюда жёсткий `max_rows` и, при больших объёмах,
хранение таблицы отдельным ключом со ссылкой из состояния.

Обязательно расширить `app/graph/invalidation.py`: rollback до `ingress` должен
чистить и SQL-артефакты тоже.

### 4.6. Ответ пользователю

В `artefacts.data` (`app/api/schemas.py`) добавить блок с `sql`, `explanation`,
`row_count`, `truncated`. Фронт (`chat/`) должен показывать запрос — иначе
пользователь не сможет проверить, что цифры взяты правильно, а на графике по
данным из базы это критично.

## 5. Безопасность

Это единственная часть системы, которая получит доступ к боевым данным, поэтому
границу лучше провести жёстко и на стороне SQL-сервиса, а не оркестратора:

- **Отдельная роль в БД, только чтение.** Никаких `INSERT`/`UPDATE`/`DELETE`/DDL
  на уровне прав, а не только на уровне промпта.
- **Валидация сгенерированного SQL** до исполнения: разрешён один
  `SELECT`-стейтмент, запрещены множественные выражения через `;`, запрещены
  системные таблицы. Промпт-инъекция через вопрос пользователя — реалистичный
  сценарий, и одного «модель обучена так не делать» недостаточно.
- **`statement_timeout` и `LIMIT`** на каждый запрос.
- **Фильтр входа guardrails уже стоит перед пайплайном** и отработает до похода в
  базу; отдельно отключать его для этой ветки не нужно.
- **В логи и трейсы не должны попадать сами данные** — только SQL, число строк и
  тайминги. Сейчас Langfuse пишет входы и выходы нод; для этой ветки понадобится
  маскирование содержимого таблицы.

## 6. Наблюдаемость

Обернуть вызов в `node_span` (`app/infra/tracing.py`), как это сделано для
guardrails. В спан класть: вопрос пользователя, сгенерированный SQL, число строк,
`truncated`, длительность. Не класть строки результата (см. выше).

## 7. Минимальная первая версия

Чтобы получить работающий сквозной сценарий быстро и не переписывать потом:

1. SQL-сервис с одним `POST /query`, вариант А (сырая таблица), захардкоженным
   подключением к одной базе и `LIMIT`. Без `need_clarification` — сначала только
   `ok` / `error`.
2. В `chart_agent`: конфиг, клиент, нода, ветка в маршрутизации. Решение о ветке
   на первом шаге можно принимать по явному признаку (например, включённый
   пользователем режим «данные из базы» в интерфейсе) — это снимает вопрос
   точности классификации и позволяет проверить весь остальной путь.
3. Дальше: `need_clarification`, автоматическая классификация интента через
   guardrails, `GET /schema`, показ SQL в интерфейсе.

## 8. Открытые вопросы к разработчику

- ~~**Одна база или несколько?**~~ **Решено: несколько.** В контракте есть
  необязательный `datasource_id`, каталог строится из `DATASOURCE_ROOTS`
  (сканирование `*.sqlite`, id = имя файла). На наборах из работы это 243 базы
  за одним сервисом. В оркестраторе — `SQL_AGENT_DATASOURCE_ID`; выбора
  источника в интерфейсе пока нет, база задаётся конфигурацией.
- **Кто владеет схемой?** Если SQL-агент сам обходит `information_schema` при
  старте — нужен механизм обновления при миграциях.
- **Права пользователя.** Сейчас у системы нет аутентификации: сессия — это
  просто UUID с фронта. Если данные в базе разграничены по пользователям, вопрос
  идентичности придётся решать до подключения этой ветки, а не после.
- **Кэширование.** Повторный одинаковый вопрос — идти в базу заново или
  переиспользовать `persisted_sql_result`? Влияет на актуальность цифр.
- **Поведение при `truncated=true`.** Строить график по части данных с
  предупреждением или требовать уточнить фильтр? Рекомендация — второе для
  агрегатов, первое для распределений.
