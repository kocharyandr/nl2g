# SQL Agent

NL2SQL-источник данных для [chart_agent](../chart_agent/). Принимает вопрос на
естественном языке, возвращает таблицу из базы. Синхронный, без состояния.

Это единственный документ по сервису. Общая картина системы — в
[../README.md](../README.md); предпосылки и разбор точки врезки — в
[../INTEGRATION_SQL_SOURCE.md](../INTEGRATION_SQL_SOURCE.md).

## 1. Зона ответственности

Сервис **поставляет только данные**. Он не решает, какой строить график, не
генерирует `matplotlib`-код и не участвует в подтверждении результата — всё это
уже умеет `chart_agent`.

Реализован **вариант А**: возвращается результат запроса как есть, без
предварительной агрегации под график. Решение «какой формы должны быть данные»
остаётся ровно в одном месте — в codegen-шаге оркестратора. Поэтому правка
«а теперь то же самое, но линией» не требует повторного похода в базу.

```text
вопрос ──► схемотехник ──► программист ──► критик ──► исполнение ──► columns + rows
             (какие          (SQL по        (правит по    (read-only,
              таблицы)        урезанной      реальной      LIMIT,
                              схеме)         ошибке БД)    timeout)
```

## 2. Почему три роли, а не один промпт

Конфигурация перенесена из исследовательской части работы, где её измеряли на
KaggleDBQA (185 вопросов):

| Конфигурация | Execution Accuracy |
| --- | ---: |
| Zero-shot | 4.9% |
| Few-shot | 13.5% |
| CoT + RAG | 49.7% |
| Мульти-агент (3 роли) | 51.4% |
| + LoRA на роли | 52.4% |
| **+ профиль схемы** | **57.3%** |

Ключевой для сервиса элемент — **критик с execution feedback**: SQL исполняется
по-настоящему, и текст ошибки SQLite (или предупреждение «вернулось 0 строк»)
возвращается модели как обратная связь, до трёх итераций. Побочный эффект
важнее метрики: наружу по построению не уходит неисполнимый запрос.

Второй по важности — **профиль схемы**: сгенерированные описания таблиц и
колонок в промпте. +4.9 п.п. без дообучения, почти целиком за счёт простых
вопросов (Easy 62.5% → 78.1%).

Честное ограничение: Hard и Extra Hard вопросы (вложенные подзапросы,
три и более JOIN) решаются на уровне 0–12%. Поэтому `sql` и `explanation`
обязательны в ответе и показываются пользователю.

## 3. API

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/query` | вопрос → таблица |
| `GET` | `/datasources` | список доступных баз |
| `GET` | `/schema` | список таблиц и колонок с описаниями (`?datasource_id=`) |
| `GET` | `/health` | доступность БД и трёх ролевых endpoint'ов |

### `POST /query`

```json
{
  "question": "выручка по регионам за прошлый квартал",
  "session_id": "uuid-сессии-из-chart_agent",
  "datasource_id": "GeoNuclearData",
  "max_rows": 5000,
  "hints": { "tables": ["orders", "regions"] }
}
```

`datasource_id` необязателен — без него берётся база по умолчанию. Каталог
источников строится из `DATASOURCE_ROOTS`: сканируются все `*.sqlite`, id
источника это имя файла без расширения. Оно же совпадает с именем файла
профиля схемы, поэтому описания таблиц подхватываются без дополнительной
настройки. Базы открываются лениво — зарегистрировать сотни файлов ничего
не стоит.

Ответ при успехе:

```json
{
  "status": "ok",
  "columns": [{"name": "region", "type": "string"}, {"name": "revenue", "type": "number"}],
  "rows": [["North", 7650.0], ["South", 2100.0]],
  "row_count": 2,
  "truncated": false,
  "sql": "SELECT region, SUM(revenue) FROM orders GROUP BY region",
  "explanation": "Суммарная выручка по регионам.",
  "meta": { "selected_tables": ["orders", "regions"], "critic_attempts": 1, "profile_used": true }
}
```

Ещё два штатных статуса: `need_clarification` с полем `question_to_user`
(включается флагом `CLARIFICATION_ENABLED`) и `error` с `error_type` из набора
`sql_error` / `llm_error` / `unsafe_sql` / `db_error` / `timeout` / `internal`.

Свойства контракта, на которые опирается оркестратор:

- **`columns` + `rows`, а не CSV-строка.** Типы приходят от базы, и определять
  их по значениям не нужно: отличить год от четырёхзначной суммы по данным
  нельзя, а СУБД это уже знает. `chart_agent` для этой ветки отключает свою
  эвристику типов.
- **`sql` и `explanation` обязательны при успехе** — они показываются
  пользователю под графиком и пишутся в трейс.
- **`truncated`** — честный флаг обрезки по `max_rows`.
- **`meta` не содержит строк результата** — только форма, тайминги и решения.

## 4. Роли и LoRA

Каждая роль ходит в **свой** OpenAI-совместимый endpoint со своим LoRA-адаптером.
В коде сервиса только HTTP — про способ инференса он ничего не знает.

### Вариант 1 — Ollama (рекомендуется)

```bash
ollama pull qwen2.5-coder:14b
make ollama-lora        # scripts/setup_ollama_lora.sh
```

Скрипт делает всю цепочку и создаёт три модели —
`nl2sql-schema`, `nl2sql-sql`, `nl2sql-critic`:

```text
MLX (lora_a/lora_b)  ──►  PEFT (lora_A/lora_B)  ──►  GGUF  ──►  ollama create
   адаптеры из ВКР        транспонирование,          llama.cpp
                          alpha = scale × rank
```

Конвертация нужна потому, что адаптеры обучались в MLX, а Ollama при
GGUF-базе принимает только GGUF-адаптер. Соответствие форматов:
MLX хранит `lora_a [in, r]` и `lora_b [r, out]`, PEFT ожидает
`lora_A.weight [r, in]` и `lora_B.weight [out, r]` — обе матрицы
транспонируются; MLX-параметр `scale` это `lora_alpha / r`, отсюда
`lora_alpha = 160` при `rank = 8`.

Все три роли обслуживает один Ollama на одном порту — они отличаются только
именем модели. Чтобы модели не выгружали друг друга:

```bash
OLLAMA_MAX_LOADED_MODELS=3 OLLAMA_KEEP_ALIVE=30m ollama serve
```

### Вариант 2 — MLX

```bash
./scripts/run_mlx_servers.sh start    # schema:8071, sql:8072, critic:8073
```

Три процесса `mlx_lm.server`, каждый с `--adapter-path` своей роли. Адаптеры
применяются ровно в том виде, в котором обучались — без конвертации. Почему три
процесса, а не один: поле `adapters` в запросе есть, но смена адаптера
перезагружает базовую модель целиком (`ModelProvider.load` кэширует по ключу,
включающему `adapter_path`), и конвейер из трёх ролей перезагружался бы на
каждом шаге.

Память: Qwen2.5-Coder-14B-Instruct-4bit ≈ 7.7 ГБ на процесс (~23 ГБ на три).
На машине поменьше — `GROUP=Qwen2.5-Coder-7B` (≈ 4 ГБ на процесс).

### Оговорка о квантовании

Адаптеры обучались на 4-битной MLX-версии базовой модели. Вариант 2 применяет
их к ней же. Вариант 1 применяет их к GGUF-квантованию Ollama — схема
квантования другая, и это отличие от измеренной в ВКР конфигурации.
На практике адаптер работает: базовая модель игнорирует инструкцию про
`<thinking>`, а версия с LoRA использует теги как обучена и выдаёт SQL в
характерном для Spider стиле (`country  =  'France'`). Но если нужны цифры,
строго сопоставимые с таблицей из §2, замеряйте на варианте 2.

## 5. Безопасность

Это единственная часть системы с доступом к боевым данным, поэтому граница
проведена здесь, а не в оркестраторе:

- **Только чтение на уровне подключения.** SQLite открывается через
  `file:...?mode=ro`; для боевой БД дополнительно нужна отдельная read-only
  роль на уровне прав, а не только промпта.
- **Валидация каждого запроса до исполнения** (`app/db/safety.py`): ровно одно
  выражение, только `SELECT` (или `WITH ... SELECT`), запрет `INSERT`/`UPDATE`/
  `DELETE`/DDL/`PRAGMA`/`ATTACH` в любом месте запроса, запрет системных
  таблиц. Строковые литералы и комментарии вырезаются до проверки, поэтому
  ни `';'`, ни `-- ;` не прячут второе выражение.
- **`LIMIT` и таймаут на каждый запрос.** Лимит ставится как `max_rows + 1`,
  чтобы честно отличить «строк ровно столько» от «строки обрезаны».
- **В логи и трейсы не попадают данные** — только SQL, число строк и тайминги.

Промпт-инъекция через вопрос пользователя — реалистичный сценарий, и «модель
обучена так не делать» здесь не считается аргументом: валидация выполняется
всегда, независимо от того, что вернула модель.

## 6. Конфигурация

Скопируйте `.env_template` в `.env`.

| Переменная | Смысл |
| --- | --- |
| `DB_BACKEND` / `DB_PATH` / `DB_ID` | база по умолчанию; реализован `sqlite` |
| `DATASOURCE_ROOTS` | каталоги с `*.sqlite` через `:`; id источника = имя файла |
| `DB_MAX_ROWS` | жёсткий потолок выборки (состояние сессии едет в Redis) |
| `DB_STATEMENT_TIMEOUT_SEC` | таймаут одного запроса |
| `PROFILES_DIR` | папка с профилями схемы (`{db_id}.json`) |
| `SCHEMA_API_BASE` / `SQL_API_BASE` / `CRITIC_API_BASE` | endpoint на роль |
| `CRITIC_MAX_ATTEMPTS` | итераций execution feedback (по умолчанию 3) |
| `USE_PROFILE` | подмешивать описания таблиц и колонок в промпт |
| `CLARIFICATION_ENABLED` | разрешить ответ `need_clarification` |
| `EXPLANATION_LLM_CALL` | отдельный короткий вызов для `explanation` |

```bash
make install                                        # .venv + зависимости
OLLAMA_MAX_LOADED_MODELS=3 ollama serve &           # если ещё не запущен

make run                                            # сервис на :8500
```

Проверка:

```bash
curl -s localhost:8500/health
curl -s localhost:8500/query -H "Content-Type: application/json" \
  -d '{"question":"топ-5 стран по числу энергоблоков","max_rows":10}'
```

Или в Docker: `make up` (роли остаются на хосте, сервис ходит на
`host.docker.internal`).

## 9. Прогон по гольд-выборке и разбор

Два скрипта для оценки качества на тестовой выборке из ВКР.

**Прогон.** [scripts/run_benchmark.py](scripts/run_benchmark.py) берёт вопросы из
`KaggleDBQA/examples/*_test.json`, прогоняет через сервис и записывает по каждому
всё нужное для суждения: сгенерированный SQL, эталонный SQL, выбранные
схемотехником таблицы, число попыток критика, оба набора строк.

```bash
scripts/run_benchmark.py -n 5 -o benchmark_results.json   # 5 вопросов на базу
scripts/run_benchmark.py -d USWildFires -n 25             # одна база целиком
```

Execution accuracy считается так же, как в ВКР — равенством множеств строк, — но
это только **предложение**: итог определяется ручной разметкой.

**Разбор.** [scripts/make_review.py](scripts/make_review.py) собирает из результата
одну самодостаточную HTML-страницу:

```bash
scripts/make_review.py benchmark_results.json -o review.html
open review.html
```

На странице по каждому вопросу видно происхождение каждого шага, SQL модели рядом
с эталонным, оба результата — и проставляются две оценки: **точность**
(верно/неверно) и **шаблон запроса** (соответствует/не соответствует эталонной
структуре). Отметки хранятся в браузере и выгружаются в CSV или JSON.

Разделение намеренное: авто-метрика ловит совпадение результата, но не отвечает на
вопрос «правильным ли способом получен ответ» — запрос может вернуть верные строки
по случайности, и наоборот, структурно верный запрос может разойтись с эталоном на
форматировании.

## 10. Состояние

Тесты: `make test` — **70 проходят**.

Проверено на живых моделях (Ollama + LoRA, база GeoNuclearData из KaggleDBQA):
запрос «сколько действующих энергоблоков во Франции» → `SELECT count(*) FROM
nuclear_power_plants WHERE country = 'France' AND status = 'Operational'` → 58,
что совпадает с прямой проверкой по базе. Время ответа 15–18 с на запрос,
критику исправления не потребовались.

Покрыто тестами: валидация SQL (включая обход через литералы и комментарии),
read-only режим подключения, определение обрезки выборки, типы колонок,
петля критика, сужение схемы, фолбэк при пустом ответе схемотехника,
контракт HTTP на реальной базе KaggleDBQA.

Не сделано осознанно, в порядке приоритета:

1. **Коннектор только SQLite.** `DBConnector` — готовый шов для PostgreSQL,
   но тексты ошибок у него другие, и петлю критика придётся перепроверить.
2. **`need_clarification` выключен по умолчанию** — первая версия отвечает
   только `ok`/`error`, как и планировалось.
3. **Нет кэширования** повторных одинаковых вопросов: влияет на актуальность
   цифр, решение зависит от требований к данным.
4. **Нет аутентификации.** Если данные в базе разграничены по пользователям,
   вопрос идентичности решается до подключения к боевому контуру.
